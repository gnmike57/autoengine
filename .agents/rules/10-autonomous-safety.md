# 10. AUTONOMOUS AI SAFETY & SANDBOXING

## AI Code Sandboxing (ABSOLUTE)
Any autonomous script or OpsSkill generated by Hermes or external LLMs MUST NEVER be executed directly via `child_process.exec()` or `eval()` in the global scope.
1. **Node.js VM Module**: AI scripts must be executed within `vm.runInNewContext(script, sandboxContext)`.
2. **Restricted Context**: The sandbox context must be explicitly injected with ONLY safe utilities (e.g., mapped `console.log`). Access to `fs`, `child_process`, `os`, and global namespaces is strictly prohibited.
3. **Timeouts**: The VM execution must be bounded by a strict timeout (e.g., 5000ms) to prevent infinite loops (e.g., `while(true)`).

## Telemetry-Driven Automatic Rollback
Hermes orchestrates dynamic timing reductions and autonomous OpsSkills. To prevent degradation:
1. **State Snapshots**: Before applying any `DynamicTimings` reduction or OpsSkill, the exact previous state MUST be persisted durably to the `ops_revisions` SQLite table.
2. **Impact Monitoring**: If the `batch_success_rate` anomaly detector fires negatively (success rates drop significantly) after a revision is applied, Hermes must instantly fetch the last stable revision, restore the `DynamicTimings`, and mark the revision as `rolled_back`.

## Self-Repair Infinite Loop Prevention
When mapping cascading DOM layout changes to specific AI repair prompts, Hermes must not enter an infinite self-repair loop:
1. **Global Cooldown**: Implement a strict 1-hour global cooldown for all self-repairs after any repair attempt, to allow metrics to stabilize.
2. **Max Attempts**: If a specific anomaly type fails >2 times in the last 24 hours, Hermes must halt self-repair and escalate to human review.
3. **Recursive LLM Prompting**: When generating a repair prompt, Hermes MUST explicitly provide the LLM with the history of its previous failed repair attempts for that specific anomaly, instructing it to attempt a radically different approach.
